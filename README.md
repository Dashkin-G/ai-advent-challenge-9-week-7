# AI Advent Challenge · неделя 7 — ассистент разработчика

## День 31. Ассистент разработчика

Ассистент отвечает на вопросы о проекте [ml-student-dropout](../ml-student-dropout) — сервисе прогноза
отчисления студентов. Команда `/help <вопрос>`: ассистент берёт у git текущую ветку и изменения через
**MCP**, находит нужные места в **README и docs/** через **RAG** и отвечает со ссылками на файлы.
Всё работает на этом компьютере: модели **qwen3.5:4b** и **bge-m3** — в Ollama, интернет не нужен.

### Как работает

```
/help где считаются причины риска?
  │
  ├─ ① контекст проекта — MCP-сервер git (в этом же приложении, /mcp/git/)
  │     git_branch · git_status · list_files, а если вопрос про изменения — ещё git_diff
  │
  ├─ ② документация — RAG по README.md и docs/*.md проекта
  │     фрагменты по заголовкам Markdown (78 штук) → векторы bge-m3 → 3 ближайших по смыслу
  │
  └─ ③ ответ — qwen3.5:4b: «контекст git + вопрос + фрагменты + вопрос»
        → ответ со ссылками вида [docs/model.md › Причины риска]
```

- **MCP вызывает код, а не модель**: на каждый `/help` — одна сессия MCP и три-четыре инструмента по
  очереди. Так ответ предсказуем, а на экране виден каждый вызов с аргументами и результатом.
- **Фрагмент — раздел документа**: Markdown режется по заголовкам `#`–`###`; длинный раздел — по
  абзацам до 900 знаков, у таблицы в каждой части повторяется шапка, блок кода не режется. Заголовок
  фрагмента — готовая ссылка для ответа: `файл › раздел`.
- **Индекс обновляется сам**: поменяли документацию — при следующем вопросе пересчитываются векторы
  только изменившихся фрагментов (кэш — `data/embeddings.json`).
- Параметры модели — из дня 29 недели 6: `temperature 0.1`, без штрафа за повторы, ответ до 512
  токенов, контекст 4 096.

### Запуск

1. Ollama запущен, модели скачаны: `ollama pull qwen3.5:4b`, `ollama pull bge-m3`.
2. Проект ml-student-dropout лежит рядом, в `../ml-student-dropout` (другой путь — переменная `PROJECT_DIR`).
3. `pip install -r requirements.txt`
4. `python -m app.main` → http://127.0.0.1:8001 (8000 оставлен самому ML-проекту; другой порт — `PORT`).

При старте приложение считает векторы документации и загружает модель в память, чтобы первый
вопрос не ждал.

### Как проверить задание

- **README и docs/ в RAG** — шаг ② показывает найденные фрагменты: файл, раздел и косинусную
  близость; щелчок раскрывает текст. В шапке шага — сколько файлов и фрагментов в индексе.
- **MCP — git-ветка** — в шапке страницы «ветка main», в шаге ① — ветка, последний коммит,
  незакоммиченные изменения и число файлов. «Вызовы MCP» раскрывают каждый вызов: инструмент,
  аргументы, результат JSON, время. Сервер отвечает по протоколу MCP 2026-07-28.
- **`/help` отвечает о структуре проекта** — примеры под полем ввода; ответ ссылается на файлы
  документации, ссылка подсвечивает фрагмент в шаге ②.

Проверить MCP без страницы — любым MCP-клиентом по адресу `http://127.0.0.1:8001/mcp/git/`.

- Все семь ответов верные. Ссылку на раздел модель ставит не всегда: в трёх ответах по документации
  из пяти; найденные фрагменты при этом всегда видны в шаге ②.
- **Время ответа — это чтение промпта**: ~1 100 токенов за 8–12 с (~120 токенов/сек на процессоре);
  генерация — 15–20 токенов/сек. MCP — 0,3 с на 3–4 вызова, поиск — 0,04 с.
- Повтор того же вопроса Ollama берёт из кэша: промпт «читается» за 0,1 с, ответ — за 7 с.

### Находки

- **Промах поиска лечится документацией.** На «какие эндпоинты есть в API?» поиск сначала принёс
  описание модулей — в таблице эндпоинтов не было самого слова «эндпоинт», — и модель придумала
  `/dataset` и `/train`. Строка «Эндпоинты сервиса — 12 штук…» над таблицей подняла её с 4-го места на
  1-е (близость 0,55 → 0,70), ответ стал верным.
- **Модели нужен разобранный контекст git.** Списком «файл (статус)» модель увидела только правку
  `.gitignore` из diff и пропустила 22 новых файла. Группы «изменены (1): …; новые (22): …» — и ответ
  полный.
- **Начало промпта не кэшируется.** В Ollama 0.40 у qwen3.5 только 8 слоёв из 32 с кэшем внимания,
  остальные хранят состояние, и общий префикс разных вопросов заново читается целиком. Кэш
  срабатывает лишь на точный повтор промпта. Дату коммита ассистент всё равно передаёт точную, а не
  «5 минут назад», — иначе контекст менялся бы каждую минуту.
- **MCP SDK 2.3**: клиент сначала пробует новый протокол 2026-07-28 (`server/discover`) и
  откатывается на старое рукопожатие. Ошибку инструмента клиент видит своими словами, только если
  сервер бросает `ToolError`; любое другое исключение SDK прячет за «Error executing tool».

### Как устроено

```
app/config.py     проект (PROJECT_DIR), адрес Ollama, модели, порт, сколько фрагментов брать
app/git_mcp.py    MCP-сервер git: git_branch, git_status, list_files, git_diff — только чтение
app/rag.py        документация → фрагменты по заголовкам → векторы bge-m3 (кэш на диске) → поиск
app/llm.py        Ollama: векторы, загрузка модели, ответ потоком со счётчиками
app/assistant.py  /help: вызовы MCP → поиск → промпт → ответ; события для страницы
app/main.py       FastAPI: страница, /api/status, /api/help (поток строк JSON), MCP на /mcp/git
static/index.html страница: поле /help, шаги ① ② ③
```

API: `GET /api/status` — проект и ветка (через MCP), Ollama и модели, индекс документации;
`POST /api/help {"text": "/help вопрос"}` — поток строк JSON: `question` → `mcp` (вызовы и время) →
`sources` (фрагменты) → `prompt` (что ушло модели) → `text`… → `done` (токены, чтение промпта,
генерация) или `error` с номером шага. Текст без `/help` — 400.

## День 32. Автоматическое ревью pull request

На каждый pull request в [ml-student-dropout](../ml-student-dropout) GitHub Actions запускает ревью.
Ассистент берёт diff и изменённые файлы через **MCP-сервер git**. В **RAG по коду и документации**
основной ветки он находит то, с чем сверять изменения. Модель **qwen3.5:4b** пишет комментарий в PR:
потенциальные баги, архитектурные проблемы, рекомендации. Задание выполняет self-hosted раннер на
этом компьютере, поэтому код и модель никуда не уходят.

### Как работает

```
pull request → GitHub Actions → раннер на этом ПК → action.yml этого репозитория
  │
  ├─ ① изменения — MCP-сервер git, в процессе ревью
  │     pr_files (файлы, +/−) · pr_diff (base...head) · read_file (файлы main и импорты новых версий)
  │
  ├─ ② RAG по main — README, docs/*.md и код *.py: 157 фрагментов, код — по функциям и классам
  │     на каждый изменённый файл три запроса → 4 фрагмента кода и 3 раздела документации
  │
  ├─ ③ ревьюер кода — diff + похожий код проекта → баги и рекомендации
  ├─ ④ ревьюер архитектуры — diff + разделы и оглавление документации → нарушения устройства
  │     проекта и устаревшая документация
  │
  └─ комментарий в PR и Summary запуска: три раздела, ссылки на строки, «Как получено ревью»
```

- **Два ревьюера вместо одного промпта.** Ревьюеру кода RAG даёт код проекта, ревьюеру архитектуры —
  документацию. Один промпт на три задачи 4B-модель выполняла через раз: из трёх проблем находила
  одну-две, и каждый раз разные.
- **Ответ — JSON по схеме.** Ollama не даёт модели отойти от формата, Markdown собирает код. Номер
  строки становится ссылкой, только если модель видела его в diff. Основание показывается, только
  если это раздел, который был в промпте.
- **Документацию проверяют отдельным полем.** Ревьюер архитектуры обязан ответить, какие файлы
  документации устарели. Для этого у него есть оглавление: поиск не всегда приносит раздел со
  списком эндпоинтов.
- **Код в RAG — по `ast`.** Фрагмент — функция или класс целиком, импорты и константы между ними —
  отдельно, у каждого фрагмента номера строк. Раздел документации, разрезанный на части, попадает
  в промпт целиком.
- `seed` закреплён: тот же PR даёт то же ревью. Ревью — совет: найденные баги задание не валят.

### Подключение

**1. Раннер на этом ПК** (один раз; папка — короткий путь, иначе `pywin32` упирается в лимит
Windows 260 знаков):

```powershell
mkdir $HOME\actions-runner; cd $HOME\actions-runner
Invoke-WebRequest https://github.com/actions/runner/releases/download/v2.338.0/actions-runner-win-x64-2.338.0.zip -OutFile runner.zip
Expand-Archive runner.zip .
$token = gh api -X POST repos/Dashkin-G/ml-student-dropout/actions/runners/registration-token --jq .token
.\config.cmd --url https://github.com/Dashkin-G/ml-student-dropout --token $token --name ai-review --unattended
```

**2. В репозитории проекта** — `.github/workflows/ai-review.yml`:

```yaml
on: pull_request
permissions: {contents: read, pull-requests: write}
jobs:
  review:
    runs-on: [self-hosted, Windows]
    steps:
      - uses: actions/checkout@v7
        with: {fetch-depth: 0}
      - uses: Dashkin-G/ai-advent-challenge-9-week-7@main
```

**3. Перед работой** — Ollama запущен (`qwen3.5:4b`, `bge-m3`), раннер — `.\run.cmd` в
`$HOME\actions-runner`. При первом запуске action создаёт venv в кэше раннера (~40 с) и считает
векторы main (~40 с), дальше берёт их из кэша.

Репозиторий публичный: чужой PR из форка тоже запустил бы задание на этом ПК. Поэтому раннер
включаем только на время работы, а в Settings → Actions → General ставим «Require approval for all
external contributors».

Без GitHub то же ревью — из командной строки:
`python -m app.review --base main --head feature/batch-predict` (проект — `PROJECT_DIR` или `--repo`,
`--out review.md` — в файл).

### Как проверить задание

- **Пайплайн запускается на PR** — вкладка Actions проекта: запуск «AI-ревью» на раннере
  `ai-review`; новый пуш в PR отменяет ревью предыдущего и запускает своё.
- **Ассистент получает diff и изменённые файлы** — в логе шага «Ревью» строка ① с вызовами MCP:
  `pr_files`, `pr_diff`, `list_files`, `read_file`.
- **RAG по документации и коду** — строка ② со списком фрагментов и близостью; в комментарии —
  «Как получено ревью».
- **Баги, архитектура, рекомендации** — комментарий в PR с тремя разделами и ссылками на строки;
  копия — в Summary запуска.

### Результат (17.10.2026, процессор)

PR `feature/batch-predict` — `POST /predict/batch`, пакетный прогноз группы. В первый коммит
заложены три проблемы, второй их исправляет.

| Коммит | Что нашло ревью | Время |
|---|---|---|
| с проблемами (4 файла, +71 −1) | деление на ноль при пустом списке; импорт FastAPI в `src/ml` вопреки `docs/architecture.md`; `docs/api.md` не описывает новый эндпоинт; тесты на пустой список и на 501 студента. Одно замечание неточное | 2 мин 20 с |
| с исправлениями (7 файлов, +118 −4) | ни одной из трёх проблем; 5–6 замечаний, почти все ошибочные | 3 мин 20 с |

- Время уходит на модель: два промпта по 4–5 тыс. токенов читаются по 33–43 с, ответы по 400 токенов
  пишутся по ~30 с. MCP — 2 с, RAG — 3 с (40 с, пока векторы main не посчитаны).
- На коде без проблем 4B-модель всё равно что-то находит, и это главный её предел. Ревью — подсказка,
  а не вердикт.

### Находки

- **Поиск по коду плохо находит документацию.** Запрос из добавленных строк ставит на первые места
  похожий код. Раздел «Модули» с правилом «модули `src/ml` ничего не знают о FastAPI» нашёлся
  только по запросу «Модуль `путь`: за что отвечает и о чём знает». Поставили оба запроса.
- **Двойная кавычка обрывала замечание.** Модель цитирует код дословно: `levels["high"]` закрывал
  строку JSON, и текст обрывался на `levels[`. В промпте двойные кавычки заменены одинарными, для
  Python это то же самое.
- **Без импортов модель их «не видит».** На исправленном коде модель писала «`STAGES` не
  импортирован»: начала файла не было в diff. Теперь у изменённых файлов кода показаны импорты.
- **Та же модель как проверяющий не работает.** Проверка замечаний третьим вызовом отбросила все 7,
  включая три настоящих. Самооценка «уверен / предположение» тоже не помогла: галлюцинации модель
  пометила уверенными, а настоящий баг — предположением. Обе идеи убраны.
- **Рассуждение (`think`) не окупилось:** +1 500 токенов, то есть +100 с, а находки те же.
- **pwsh не останавливается на ошибке программы.** Упавший `pip install` шёл дальше, поэтому после
  него стоит явная проверка `$LASTEXITCODE`.

## День 33. Ассистент поддержки пользователей

Мини-сервис поддержки для [ml-student-dropout](../ml-student-dropout). Клиенты сервиса — сотрудники
вузов, их обращения лежат в CRM: это JSON-файл, который ассистент читает через **MCP-сервер crm**.
Оператор выбирает обращение, и ассистент пишет черновик ответа клиенту. Он опирается на **RAG по FAQ
поддержки и документации проекта** и учитывает **клиента и тикет**: технические данные, роль, прошлые
обращения. Модели те же — qwen3.5:4b и bge-m3 в Ollama.

### Как работает

```
оператор выбирает обращение T-1041 → «Ответить»
  │
  ├─ ① данные из CRM — MCP-сервер crm (в этом же приложении, /mcp/crm/) читает support/crm.json
  │     get_ticket — сообщение, статус и технические данные: запрос, ответ сервиса, лог
  │     get_user — роль, вуз, как работает с сервисом, заметки поддержки, прошлые обращения
  │
  ├─ ② база знаний — RAG по support/faq.md (17 вопросов) + README и docs/ проекта: 98 фрагментов
  │     два запроса — вопрос и текст ошибки из тикета, у фрагмента лучшая близость → 3 фрагмента
  │
  └─ ③ ответ клиенту — qwen3.5:4b: «данные CRM + вопрос + фрагменты + вопрос»
        → по имени, с причиной из тикета, со ссылками вида [FAQ › Что значит ошибка 422?]
```

- **Очередь — тоже через MCP**: `list_tickets`. «Вопрос о продукте» в конце очереди — без тикета:
  CRM не вызывается, ответ только по базе знаний.
- **MCP вызывает код**, как в `/help`: `get_ticket`, затем `get_user` в одной сессии.
- **CRM** — 6 клиентов из трёх вузов, 7 открытых обращений и 2 решённых. Тексты ошибок 422, 400 и
  500 в тикетах сняты с работающего ML-сервиса. Часть причины лежит не в тикете, а в профиле или
  истории клиента: сервер без интернета, запуск командой `uvicorn src.main:app --reload`. Файл
  читается на каждый вызов, другой файл — переменная `CRM_FILE`.
- **FAQ** — вопросы клиентов по одному на раздел `##`, заголовок раздела становится ссылкой.
  Ответы сверены с кодом ML-сервиса.
- `seed` закреплён: то же обращение — тот же ответ.

### Запуск

`python -m app.main` → http://127.0.0.1:8001/support (страница `/help` дня 31 осталась на `/`).

### Как проверить задание

- **Ответы о продукте** — «Вопрос о продукте» в очереди: примеры вопросов, ответ по базе знаний.
- **RAG по FAQ и документации** — шаг ②: фрагменты FAQ и docs/ с близостью. У тикета с ошибкой
  сервиса видна строка «Искали ещё по ошибке из обращения». Ссылка в ответе подсвечивает фрагмент.
- **Контекст пользователя и тикета** — шаг ①: клиент, роль, как он работает с сервисом, прошлые
  обращения, технические данные. Ответ называет причину из тикета: поле, значение, адрес.

## День 34. Ассистент для работы с файлами проекта

Ассистент сам работает с файлами [ml-student-dropout](../ml-student-dropout). Задачу ставят словами —
«обнови документацию после изменений в коде», — а какие файлы искать, читать и править, решает
модель. У неё два набора инструментов: **MCP-сервер files** (поиск, чтение, правка, создание файлов) и
**MCP-сервер git** (изменения, история). Модель вызывает их сама — function calling в Ollama. Правки
копятся в черновике, страница показывает их diff, а в файлы проекта они попадают по кнопке
«Применить». Модель та же — qwen3.5:4b.

### Как работает

```
«Обнови документацию после изменений в коде» → «Выполнить»
  │
  ├─ контекст — код спрашивает MCP: ветка, незакоммиченные изменения, список файлов
  │
  ├─ ① ход работы — qwen3.5:4b сама выбирает инструменты, до 12 ходов
  │     files: list_files · read_file · search · edit_file · write_file
  │     git:   git_status · git_diff · git_log
  │     например: git_diff → search «MAX_BATCH|500|1000» → read_file → edit_file ×3
  │     после правок код один раз просит проверить их поиском
  │
  ├─ ② отчёт — что нашла (`файл:строка`) и что изменила
  │
  └─ ③ изменения — черновик MCP-сервера files: diff каждого файла
        «Применить» → apply_draft записывает файлы · «Отменить» → discard_draft
```

- **Шаги выбирает модель.** Код передаёт ей инструменты MCP-серверов как есть: имя, описание и
  JSON Schema. Потом он исполняет её вызовы и возвращает результат. Сам код зовёт MCP только в начале
  (контекст) и в конце (черновик). В «Что получила модель» видно, что модели дали только задачу,
  контекст git и инструменты.
- **Черновик.** `edit_file` и `write_file` меняют копию файла в памяти MCP-сервера. Чтение и поиск
  правки уже видят, поэтому модель может себя проверить. На диск правки пишет `apply_draft`, но модели
  этот инструмент не дан: его вызывает кнопка «Применить».
- **Правка — точной заменой**: `old` должен встречаться в файле один раз. Модель склеивает строки
  абзаца в одну — тогда текст ищется без учёта переводов строк, а перенос ставится на прежнее место.
  Номера строк, скопированные из `read_file`, отрезаются. Переводы строк файла сохраняются: в проекте
  включён `core.autocrlf`, и в рабочей папке есть и CRLF, и LF.
- **Ограничения**: пути только внутри проекта, `.git` недоступен, существующий файл через
  `write_file` не перезаписать. Повторный одинаковый вызов не исполняется: модель получает его прошлый
  результат или ошибку.
- **Типовые задачи** — в системном промпте коротким порядком действий: «где используется», «обнови
  документацию по коду», «составь CHANGELOG». Модель выбирает, какой порядок подходит к задаче.
- `seed` закреплён: та же задача на том же состоянии проекта даёт те же шаги и тот же diff.

### Запуск

`python -m app.main` → http://127.0.0.1:8001/files (страницы `/` и `/support` остались).

### Как проверить задание

- **Ассистент сам инициирует работу с файлами** — шаг ①: каждый ход модели, инструмент, аргументы,
  результат и время. Задача ставится на уровне цели, примеры — под полем ввода.
- **Читать, искать, анализировать** — `read_file`, `search` по всем файлам проекта. Отчёт ②
  группирует места по файлам, а ложные совпадения (код ответа 500 при поиске числа 500) модель
  отсеивает сама.
- **Создавать и изменять файлы** — `write_file` создаёт `CHANGELOG.md`, `edit_file` правит
  `README.md` и `docs/api.md`. После «Применить» `git status` проекта показывает изменённые файлы.
- **Минимум два сценария** — три: «где используется», «обновить документацию по изменениям в коде»,
  «сгенерировать CHANGELOG». Изменения выводятся как diff в ③.
- **Повторяемость** — каждый сценарий запущен дважды на одном состоянии проекта: вызовы, diff и отчёт
  совпали.
- MCP-сервер files доступен любому MCP-клиенту по адресу `http://127.0.0.1:8001/mcp/files/`: пять
  инструментов для модели и три для черновика.

### Находки

- **Модель искала по-русски.** В пробе без подсказок она искала «пакетный прогноз» и находила 2 места
  из 8 — до `predict_batch` не догадалась. Помогло правило «ищи так, как написано в файлах: имена из
  кода, несколько вариантов через |»: теперь находится 22 совпадения в 7 файлах.
- **Читать файлы целиком — медленно и мимо.** Без подсказки модель читала файлы целиком: 5 тыс.
  токенов за 49 с. Нужный раздел `docs/api.md` в первые 150 строк не попадал. Теперь порядок
  «сначала search, потом read_file по номерам строк», а окно чтения — 80 строк.
- **Документация пишет значения, а не имена констант.** По diff `MAX_BATCH = 500 → 1000` модель
  искала `MAX_BATCH` и правила одно место из трёх. Подсказка «поменялось число — ищи прежнее значение»
  дала запрос `MAX_BATCH|500|1000`.
- **Проверку себя из промпта 4B-модель пропускает.** В части прогонов она поправила 2 места из 3 и
  закончила. Теперь после правок код один раз просит проверить их поиском; что искать, решает модель.
  Это +1–2 хода, ~15 с.
- **Склеенные строки и честный отчёт.** Правка предложения, разбитого переносом, не находилась. Модель
  повторяла тот же вызов, а в отчёте писала, что исправила. Теперь текст ищется без учёта переводов
  строк, повтор вызова получает прежнюю ошибку, а в отчёте — «только правки, которые прошли».
- **История «новые сверху» сбивает модель.** Второй «init commit» (весь сервис, 17.10) модель упорно
  ставила в конец журнала и давала ему дату первого коммита или выдумывала свою. Правило «не
  переставляй» и пример формата не помогли. С `git_log(oldest_first=true)` все даты верны, поэтому

- **По вложенному JSON модель теряет порядок** и дублирует записи. Списки теперь приходят ей по строке

- **Ответ зависит от состояния проекта.** Контекст — это изменения и список файлов, поэтому после

## День 35. Реальная задача: ежедневная сводка новостей по теме

Чтобы следить за узкой темой — политиком, законопроектом, компанией, — приходится каждый день листать
десятки изданий: одна новость выходит в пяти местах, а нужная тонет среди тысяч других. Сервис «Сводка»
делает это сам. Пользователь регистрируется и пишет тему, а каждый вечер в 20:00 по Москве в кабинете
появляется сводка за сутки: главное в двух-трёх предложениях и сюжеты со ссылками на все издания, которые о
них написали. Сервис круглосуточно работает на VPS и читает RSS-ленты 24 изданий. Код — папка `news/`,
отдельное от ассистента приложение; модель — qwen3.7-plus в DashScope.

### Как работает

```
тема «Кирилл Дмитриев»
  └─ ИИ разбирает тему: что к ней относится и по каким ключам искать —
     «дмитриев», «кирилл дмитриев», «глава рфпи»… (ключи можно поправить)

сборщик, каждые 15 минут: RSS 24 изданий → SQLite, ~5 000 новостей в сутки

каждый день в 20:00 по Москве или по кнопке «Собрать сейчас»:
  ├─ ① новости за сутки — из базы сборщика                      1 565 из 22 изданий
  ├─ ② по словам темы — код ищет ключи в заголовках и лидах     14 кандидатов
  ├─ ③ ИИ: о теме — модель читает каждого кандидата и решает,   14 о теме,
  │     о теме ли он; почему отброшен — пишет коротко           у отказов — причина
  └─ ④ ИИ: сюжеты — склеивает одну новость из разных изданий,   4 сюжета по 2–6 изданий
        пишет 1–2 предложения на сюжет и «главное за сутки»
```

- **ИИ — там, где нужен смысл**: разобрать тему, отличить новость о теме от упоминания вскользь или
  однофамильца, написать сводку. Сбор лент и поиск по ключам делает код: прогонять через модель 5 000
  новостей в сутки дорого, а кандидатов обычно 5–80.
- **Пайплайн, а не агент**: каждый вечер те же шаги, цифры на каждом шаге, `seed`.
- **Ключи — основами слов**: «набиуллин» находит все падежи, ключ из нескольких слов — новость, где есть
  все его слова. Модель проверяет не больше 80 кандидатов, самых точных: редкий ключ весит больше частого,
  совпадение в заголовке считается дважды.
- **Лиды со страниц**: у РИА, Ленты и Ведомостей в RSS только заголовок — кандидатам лид берётся из
  `og:description` страницы новости.
- **Аккаунты**: пароль — scrypt с солью, сессия — случайный токен в cookie (HttpOnly, SameSite=Lax, на
  сервере Secure), в базе — его sha256. Попытки входа и регистрации ограничены по адресу; тем — 3 на
  пользователя и 50 на сервис, «Собрать сейчас» — раз в 10 минут: каждая сводка — платные токены.
- **Расписание** — в том же процессе: после 20:00 по Москве сводка собирается по каждой теме, у которой
  её сегодня ещё не было. Сервер был выключен — соберёт, как включится; сбой модели — повтор через полчаса.

### Запуск

- Локально: ключ модели `DASHSCOPE_API_KEY=…` в `.env` в корне, `python -m news.main` →
  http://127.0.0.1:8002.
- На сервер: `bash news/deploy.sh <IP>` из Git Bash. Скрипт копирует код, ставит Python-окружение, службу
  `news` (systemd) и Caddy с HTTPS на `<IP через дефисы>.sslip.io`; повторный запуск обновляет код за 15 с.
  На сервер уходит только ключ модели — в `/etc/news.env`, его читает один root. Журнал —
  `sudo journalctl -u news -f -o cat`.
- Сейчас сервис открыт на https://91-188-212-182.sslip.io (VPS h3llo.cloud: Ubuntu 24.04, 1 vCPU, 2 ГБ).

### Как проверить задание

- **Какую задачу решали** — ежедневная сводка по узкой теме из 24 изданий вместо ручного просмотра лент.
- **Как участвует ИИ** — три шага: разбор темы («Как ИИ понял тему» и ключи), отбор по смыслу (шаг ③ и
  «Как собрано»: что отброшено и почему), сюжеты и «главное за сутки» (шаг ④). Цифры шагов — над сводкой.
- **Реальное окружение** — VPS с HTTPS, живые ленты, открытая регистрация, сводки по расписанию.

### Находки

- **Ленты держат часы, а не сутки**: ТАСС, РИА, RT, МК — 2–4 часа (75–100 новостей), Коммерсантъ — 3 суток.
  Поэтому сборщик обходит ленты каждые 15 минут и копит новости, а не читает их в момент сводки.
- **Известия закрыты DDoS-Guard для адресов дата-центров**: с сервера 403 даже на главную, в том числе с
  браузерным User-Agent. С ноутбука напрямую отвечают, но на частые запросы — 429. Из списка убраны.
- **У МК время на час впереди** — новость «из будущего» считается вышедшей в момент обхода.
- **Одна новость дважды в ленте** (статья и видео) — проверяется один раз.
- **qwen3.8 оборачивала JSON в ```json … ```**, хотя `response_format` — `json_object`; с `seed` три
  повтора давали тот же ответ. Теперь JSON берётся между первой `{` и последней `}`, а повтор идёт без `seed`.
- **Фамилия — отдельным ключом**: заголовки пишут «Дмитриев заявил…» без имени. С одним ключом
  «кирилл дмитриев» находилось 11 кандидатов из 18.
- **qwen3.7-plus брала общие ключи** («санкци», «встреч», «россия», «сша») вопреки правилу в промпте:
  155 и 440 кандидатов, 15–16 тыс. токенов на сводку. Помогли примеры ключей в промпте (19 и 22 кандидата,
  6–7 тыс. токенов) и вес по редкости ключа: даже при общих ключах модель читает самые точные совпадения.
- **Бесплатная квота кончилась посреди проверок**: у qwen3.8-2.4t-a95b — 403 «Free quota exhausted», у
  qwen3.8-flash квоты не было совсем. Stop-on-Exhaust не дал списать деньги; работает qwen3.7-plus, у
  которой квота осталась.

### Как устроено (новое)

```
news/config.py          издания, расписание, модель, лимиты; .env читает сам

news/digest.py          разбор темы, шаги ①–④, расписание 20:00
news/llm.py             DashScope: JSON-ответ, бюджет размышлений, повторы

news/db.py              SQLite: users, sessions, topics, articles, digests
news/main.py            FastAPI: страница и API; сборщик и расписание — фоном в том же процессе
news/static/index.html  вход и регистрация, темы, шаги ①–④, сводка, архив, «Как собрано»
news/deploy.sh          выкладка на VPS: venv, systemd, Caddy с HTTPS
```

API: `POST /api/register`, `/api/login` `{"email", "password"}`, `POST /api/logout`, `GET /api/me`;
`GET /api/status` — сборщик и база, без входа; `GET /api/topics`, `POST /api/topics {"query": "…"}` — тему
разбирает модель; `PUT /api/topics/{id} {"description", "keywords"}`; `DELETE /api/topics/{id}`;
`GET /api/topics/{id}/digests` — архив; `GET /api/digests/{id}`; `POST /api/topics/{id}/run` — поток строк
JSON: `articles` → `candidates` → `judge`… → `writing` → `done` или `error`.
